# AGENTS.md — Conventions for the Live API frontend sample

This file tells future coding agents (and humans) how to work in this folder
without breaking the design constraints.

## The single source of truth

All wire types come from one proto file:
**`../client_server_messages.proto`** (staged into `proto/` at codegen time).

Rules:
- Never hand-write a TypeScript interface or Python dataclass that mirrors a
  message defined in `client_server_messages.proto`. Use the generated
  bindings under `gen/` (TS) or `server/gen/` (Python) instead.
- Never edit anything under `gen/` or `server/gen/` directly. They are
  regenerated by `npm run gen` (`codegen.sh`).
- If the wire schema needs a change, edit `../client_server_messages.proto`
  (and `../client_server_messages.md` to match), then re-run codegen.

## Wire model (memorize before changing the WS code)

| Channel | Encoding | Schema |
|---|---|---|
| `/ws` (browser ↔ this server) | **binary protobuf** | `ClientMessage` / `ServerMessage` |
| upstream `/ws` (this server ↔ public Live API) | **JSON protobuf** | same |
| `/project_info`, `/models`, `/start`, `/stop` | JSON | hand-rolled |
| `/api/recordings`, `/api/load`, `/api/upload` | JSON | hand-rolled |

The server `live_api_session.py` is the only file that converts between
binary and JSON forms. Browser code never sees proto-JSON.

## Deletions that should stay deleted

These were removed from the internal app on purpose. Do not add them back
without first updating this file and the README:

| Removed | Why |
|---|---|
| `beyond` and `groot` backends | Internal-only Stubby/blade endpoints; not relevant to OSS users. |
| MCP servers and tool execution | The public reference doesn't configure tools; the model never emits `toolCall`. |
| Tool-call / tool-response rendering on the frontend | Same reason as above. |
| `recordio` recording format | Replaced with a portable length-prefixed binary proto file. |
| Closure Library `Queue` / `safevalues` | Replaced with a tiny inline queue; safevalues isn't needed without google3 sanitization context. |
| The internal `session_manager.py` | Replaced by `server/live_api_session.py` (smaller, public-only). |

## TypeScript: `@bufbuild/protobuf` patterns

This codebase uses `@bufbuild/protobuf` v2 (the modern protobuf-ES). Key
patterns the agent should use:

```ts
import {create, toBinary, fromBinary} from '@bufbuild/protobuf';
import {ClientMessageSchema, BlobSchema} from '../gen/client_server_messages_pb.js';

// Build a message:
const msg = create(ClientMessageSchema, {
  messageType: {
    case: 'realtimeInput',
    value: {audio: create(BlobSchema, {mimeType: 'audio/pcm;rate=16000', data: bytes})},
  },
});

// Encode binary for sending on a WebSocket:
const bytes = toBinary(ClientMessageSchema, msg);

// Decode binary on receive:
const decoded = fromBinary(ServerMessageSchema, new Uint8Array(buffer));
if (decoded.messageType.case === 'serverContent') {
  const sc = decoded.messageType.value;  // typed access; oneof discriminated
  if (sc.modelTurn) { ... }
}
```

Anti-patterns to avoid:
- `decoded.serverContent` — that's the old JSPB shape. Use
  `decoded.messageType.case === 'serverContent'` and read `messageType.value`.
- Calling `getXxx()` / `setXxx()` — that's JSPB. Use property access.
- `new SomeMessage()` — use `create(SomeMessageSchema, {...})`.

## Python: standard `google.protobuf`

`server/gen/*_pb2.py` are the standard `google.protobuf` python bindings.
Use them as you'd expect:

```python
from gen import client_server_messages_pb2 as pb
from google.protobuf import json_format

msg = pb.ClientMessage()
json_format.ParseDict({'setup': {...}}, msg)
binary = msg.SerializeToString()
```

Use `json_format.ParseDict` with `ignore_unknown_fields=False` when accepting
input from the browser (catches field-name typos as a 400 instead of a
silent drop).

## Proto-JSON gotchas (relevant when editing the proto)

These follow the proto3 JSON mapping spec; surface them in any docstring you
write that touches a JSON shape:

- Field names: snake_case in the `.proto` file becomes **camelCase on the
  wire**. E.g. `realtime_input` in the proto is `realtimeInput` in JSON.
- `int64` / `uint64` / `int32` (when large) is serialized as a **string** in
  JSON to avoid JS precision loss. E.g. `triggerTokens: "100000"`. Build
  helpers should `String(...)` numeric inputs that map to int64 fields.
- Enums: serialized as **string names** by default (e.g. `"AUDIO"`, not `1`).
- `oneof`: exactly one variant must be set per frame. Setting two is
  undefined behavior and may be silently dropped.

## Audio playback contract

`src/audio.ts` defines `PlaybackItem` (a discriminated union) that the
WebSocket client enqueues to. If you add a new event type the playback loop
should react to, **add it to the union** and the drain loop's switch will
fail to compile if you miss the handler — that's the safety check.

## Regenerate-or-fail discipline

Always run `npm run gen` after editing any `.proto`. If you didn't, `tsc
--noEmit` or `python3 -m py_compile server/server.py` will fail.

When in doubt:
```bash
npm run gen && npm run typecheck && python3 -m py_compile server/*.py
```
